## 对话 1 · 09:28

### 用户

你知道最新的jev模型吗

### AI

知道！你说的应该是 **Jev**，由 TypeSafe AI 在 **2026 年 9 月 15 日**发布的新型 AI 模型。

它和我们之前讨论的 GPT、Claude、DeepSeek 很不一样，而且与你研究的 **Agent 工作流、Token 成本优化、自动化客服**都有关系。

## 1. Jev 是什么？

Jev 被 TypeSafe AI 称为第一款 **System One Model（系统一模型）**。

它最大的特点是：

> **不负责生成长篇文字，而是专门负责快速做出结构化判断。**

例如，传统 LLM：

```text
用户：
这个客户的问题应该交给哪个部门？

GPT：
根据客户描述，我认为这个问题
可能属于技术支持部门，因为……
```

Jev：

```text
输入：
客户的问题描述

预设选项：
A. 技术支持
B. 财务
C. 销售

输出：
技术支持

置信度：
96%
```

这里的 96% 只是示意，并非实际测试结果。

Jev 可以返回选项、评分或概率，而不是生成自由文本。:chatgpt-content-reference{index="0"}

## 2. 它为什么值得关注？

TypeSafe AI 公布的主要特点如下：

| 指标 | Jev |
|---|---|
| 发布时间 | 2026 年 9 月 15 日 |
| 模型类型 | System One Model |
| 主要能力 | 分类、选择、评分、概率判断 |
| 响应时间 | 官方宣称约 70–500 毫秒 |
| 输入价格 | 官方公布 $0.042 / 百万 Token |
| 输出 | 不生成普通文本，官方公布不收取输出 Token 费用 |

这些速度和价格属于发布方公布的数据，不能直接理解成它在所有任务上都比 GPT 或 Claude 更快、更准确。:chatgpt-content-reference{index="1"}

## 3. 它和你之前学习的 Agent 有什么关系？

这才是最有意思的部分。

你之前理解的 Agent：

```text
用户任务
   ↓
GPT / Claude
   ↓
决定调用哪个 Tool
   ↓
执行
   ↓
Model 再判断
```

如果引入 Jev，可以变成：

```text
用户任务
   ↓
Jev
【判断任务类型】
   ↓
   ├─ 简单问题 → 普通程序
   │
   ├─ 复杂问题 → GPT / Claude
   │
   └─ 特殊问题 → 专业 Agent
```

也就是说，Jev 有机会承担 Agent 系统中的一部分**决策层工作**，而 GPT、Claude 等 LLM 继续负责复杂推理、生成代码和解释问题。

不过 Jev 的判断并不保证正确，实际应用仍需要设置置信度阈值和错误处理机制。

但要注意：**Empty Branch 这种能够用 C# 精确判断的问题，仍然没有必要调用 Jev。**

Jev 更值得尝试的地方，是那些传统代码难以准确分类、但又不值得启动完整 LLM Agent 的任务。

## 对话 2 · 10:08

### 用户

所以目前大模型的类型一共有多少种

### AI

目前**大模型没有一个公认的固定分类数量**。因为我们可以按照不同维度分类：输入输出形式、模型能力、工作方式、模型架构、部署位置等。

例如 GPT、Claude、DeepSeek、Qwen、V-JEPA、Jev，它们并不一定属于同一个分类维度。

结合你最近研究的 Agent、Grasshopper、具身智能和本地模型，我建议你先掌握下面这套分类体系。

# 一、按模型的核心能力分类

这是对初学者最有帮助的一种分类方式。

| 类型 | 核心能力 | 代表模型或模型家族 | 典型应用 |
|---|---|---|---|
| 1. 语言模型（LLM） | 理解和生成文字 | GPT、Claude、DeepSeek、Qwen | 对话、写作、代码 |
| 2. 推理模型 | 多步骤分析和解决复杂问题 | GPT 推理模型、DeepSeek-R1 | 数学、编程、复杂决策 |
| 3. 多模态模型（MLLM） | 理解多种信息形式 | GPT、Gemini、Qwen-VL | 图像理解、视频分析 |
| 4. 图像生成模型 | 生成或编辑图像 | FLUX、Stable Diffusion | 建筑效果图、概念设计 |
| 5. 视频生成模型 | 生成视频和动态场景 | Sora、Veo、Wan | 建筑动画、视频制作 |
| 6. 语音模型 | 理解或生成语音 | Whisper、音频生成模型 | 语音助手、实时客服 |
| 7. Embedding 模型 | 把信息转换成向量 | BGE、Qwen Embedding | RAG、知识库搜索 |
| 8. Reranker 模型 | 对搜索结果重新排序 | BGE Reranker | 提高知识库检索准确率 |
| 9. 世界模型（World Model） | 学习环境状态及其变化规律 | V-JEPA 系列 | 机器人、具身智能 |
| 10. 动作模型（Action Model） | 根据环境和目标生成动作 | RT 系列、π 系列 | 机器人控制 |
| 11. 分类/决策模型 | 从候选项中选择或评分 | Jev、各类分类模型 | Agent 路由、任务分配 |

**注意：这 11 类不是互斥的，也不是官方统一分类。** 一个模型可能同时属于语言、推理和多模态模型。

例如，GPT 可以既是语言模型，也是多模态模型，还能具备推理能力。

# 二、从 Agent 视角看，最值得理解的是这 6 类

你之前一直在研究：

```text
Agent
├─ Model
├─ Tools
├─ Skills
├─ Session
└─ Agent Loop
```

但这里的 Model 并不一定只有 GPT 或 Claude。

未来，一个 Agent 可能同时调用多个不同类型的模型。

## ① LLM：负责理解、推理和生成

例如：

```text
用户：
帮我分析这个 Grasshopper Definition。

        ↓

      LLM

        ↓

理解问题
分析结构
生成诊断
解释解决方案
```

它是目前大多数通用 Agent 的主要智能来源。

---

## ② 决策模型：负责快速选择

例如 Jev 这类面向结构化判断的模型。

```text
用户输入
   ↓
决策模型
   ↓
判断任务类型
   │
   ├─ Coding
   ├─ Debug
   ├─ Research
   └─ Documentation
```

它可能适合 Agent 的任务路由。

但不代表必须额外使用一个决策模型。简单路由完全可以通过普通程序实现。

---

## ③ Embedding 模型：负责把信息转换成向量

你之前问过 Embedding 是什么。

它可以把文字、代码或其他信息转换成数学向量：

```text
Grasshopper Data Tree
        ↓
Embedding Model
        ↓
[0.12, -0.38, 0.91, ...]
```

这样系统就可以根据语义相似度寻找相关资料。

例如：

```text
用户：
为什么 Flatten 后路径不对？

        ↓

Embedding
        ↓

搜索 GH 知识库
        ↓

找到相关文档
        ↓

交给 LLM
        ↓

生成解释
```

这就是 RAG 系统常见的工作方式。

---

## ④ Reranker：负责判断哪些资料更相关

假设 Embedding 搜索出了 20 篇文档。

Reranker 可以重新评估：

```text
搜索结果
   ↓
Reranker
   ↓
重新排序
   ↓
选择最相关的 3 篇
   ↓
LLM
```

Embedding 和 Reranker 的区别：

**Embedding 负责快速找到候选内容；Reranker 负责进一步判断候选内容的相关程度。**

---

## ⑤ 多模态模型：负责理解图像、视频和其他信息

这对你的建筑设计背景尤其重要。

例如：

```text
Grasshopper Canvas 截图
        ↓
多模态模型
        ↓
识别 Component
理解连接关系
分析错误信息
        ↓
生成诊断
```

它和传统的纯文本 LLM 最大的区别是：

**输入不再局限于文字。**

不过，针对 GH 插件，如果能够直接通过 Grasshopper SDK 获取真实组件和连接信息，通常比单纯依赖截图识别更可靠。

---

## ⑥ 世界模型：负责理解环境变化和预测

这是你之前研究具身智能时值得重点关注的方向。

例如：

```text
机器人
   ↓
摄像头观察环境
   ↓
World Model
   ↓
预测：
如果机械臂向前移动，
物体会发生什么变化？
   ↓
规划动作
```

世界模型不等于普通聊天 LLM。

它更关注：

> **环境是什么状态？采取行动后，环境可能变成什么状态？**

这对于机器人、自动驾驶、物理仿真等领域很重要。

# 三、还有一种分类：按模型架构划分

这一层偏技术原理。

| 架构 | 简单理解 |
|---|---|
| Transformer | 现代语言模型的重要基础架构 |
| Diffusion | 图像、视频等生成任务中广泛使用 |
| MoE（混合专家） | 通过路由机制选择部分专家网络参与计算 |
| Mamba / SSM | 基于状态空间模型的序列建模路线 |
| 混合架构 | 组合不同网络结构或计算机制 |

这里需要特别注意：

**MoE 和 Transformer 不一定是互斥关系。**

一个模型可以同时采用 Transformer 和 MoE。

# 四、从你的 GH Agent 产品来看，未来可能不是一个模型，而是一组模型

这是我觉得你现在最值得建立的认知。

你之前的理解：

```text
GH Agent
   ↓
GPT
   ↓
Tools
```

可以进一步升级为：

```text
                GH Agent
                   │
                   ▼
             Model Router
                   │
       ┌───────────┼───────────┐
       ▼           ▼           ▼
   决策模型      Embedding     LLM
       │           │           │
    任务分类     知识库检索    复杂推理
       │           │           │
       └───────────┼───────────┘
                   ▼
              GH Tools
                   │
                   ▼
             Grasshopper
```

再进一步：

```text
                GH Agent
                   │
       ┌───────────┼────────────┐
       ▼           ▼            ▼
     C#规则      本地小模型    云端强模型
       │           │            │
    精确检测     简单分析     复杂诊断
       │           │            │
       └───────────┼────────────┘
                   ▼
               最终结果
```

这样你就不必让一个昂贵的大模型承担所有任务。

**对于 Data Tree Debug Agent，C# 规则 + LLM 是最值得先验证的基础组合；Embedding、Reranker、决策模型等应该在知识库检索或任务路由确实出现需求后再引入。**

## 最后，你可以用这张表记住整个 AI 技术栈

| 层级 | 解决什么问题 |
|---|---|
| **Model** | 提供智能能力 |
| **API** | 让程序调用模型或其他服务 |
| **Harness** | 组织模型、工具、上下文和执行循环 |
| **Agent** | 利用模型和工具完成目标 |
| **Multica** | 管理、配置和调度多个 Agent 的工作 |
| **Git / Worktree** | 管理和隔离代码开发 |
| **GH Plugin** | 将这些能力接入 Grasshopper |

你现在可以把一个很重要的观念记下来：

> **未来的 Agent 不一定是“一个 Agent + 一个大模型”，也可能是“一个 Agent + 多种专用模型 + 多种工具”。**
>
> 模型负责不同类型的智能，Harness 负责组织它们，Agent 负责围绕用户目标完成任务。

## 对话 3 · 10:29

### 用户

现在一个 Agent 可以同时调用多个不同类型的模型吗？

### AI

**可以，而且这正是多模型 Agent（Multi-Model Agent）的重要设计方向。**

但需要先区分两个概念：

- **Multi-Model Agent：一个 Agent 调用多个模型。**
- **Multi-Agent System：多个 Agent 协同完成任务。**

它们不是一回事。一个 Agent 完全可以同时具备调用 GPT、Claude、Embedding 模型、视觉模型和本地模型的能力。

## 一、一个 Agent 怎么调用多个模型？

你之前理解的 Agent 可能是：

```text
用户
 ↓
Agent
 ↓
GPT
 ↓
Tools
 ↓
结果
```

实际上可以设计成：

```text
                  用户
                   │
                   ▼
                 Agent
                   │
             Model Router
                   │
       ┌───────────┼────────────┐
       ▼           ▼            ▼
    GPT/Claude   Embedding    视觉模型
       │           │            │
    复杂推理     知识检索      图像理解
       │           │            │
       └───────────┼────────────┘
                   ▼
                Tools
                   │
                   ▼
                最终结果
```

这里的 **Model Router（模型路由器）**负责决定什么任务交给什么模型。

但 Router 不一定本身就是 AI 模型，它也可以是普通代码。

---

## 二、多个模型有三种常见协作方式

### 方式 1：按任务分工调用

这是最容易理解的方式。

例如你的 GH Data Tree Debug Agent：

| 遇到的问题 | 处理方式 |
|---|---|
| 检查 Empty Branch | C# 规则 |
| 搜索相关 GH 文档 | Embedding 模型 |
| 分析复杂 Data Matching 问题 | GPT / Claude |
| 理解用户上传的 GH 截图 | 视觉模型 |
| 生成修改建议 | GPT / Claude |

工作流：

```text
用户：
为什么我的 Grasshopper 数据树出错了？
                    │
                    ▼
              GH Agent
                    │
                    ▼
             C# Analyzer
                    │
           ┌────────┴────────┐
           ▼                 ▼
       简单错误           复杂错误
           │                 │
        C# 修复          LLM 分析
           │                 │
           └────────┬────────┘
                    ▼
                最终结果
```

**注意：不是每个任务都必须调用所有模型。**

只调用真正需要的模型，才有机会降低成本。

### 方式 2：多个模型并行分析

例如：

```text
用户提交复杂 GH Definition
              │
              ▼
           GH Agent
              │
     ┌────────┴────────┐
     ▼                 ▼
   GPT               Claude
     │                 │
  分析错误 A         分析错误 B
     │                 │
     └────────┬────────┘
              ▼
         合并分析结果
              │
              ▼
          最终诊断
```

这种方式适合需要独立分析或交叉检查的任务。

不过，**并行调用两个模型通常会增加 Token 成本**，也不保证结果一定更准确。

### 方式 3：模型接力

一个模型完成前置工作，另一个模型接着处理。

例如：

```text
用户上传 GH 截图
        │
        ▼
     视觉模型
        │
  提取组件和连接信息
        │
        ▼
      LLM
        │
    分析潜在问题
        │
        ▼
    GH SDK Tools
        │
  检查真实数据树结构
        │
        ▼
      LLM
        │
    生成最终诊断
```

这种方式在建筑设计领域有很大的应用空间，因为建筑工作流经常同时包含图像、文字、几何和结构化数据。

# 三、那么一个 Agent 调用多个模型，需要多个 API Key 吗？

**不一定，取决于你使用什么模型服务。**

假设你的 Agent 同时使用 GPT、Claude 和本地 Qwen。

```text
                GH Agent
                   │
        ┌──────────┼──────────┐
        ▼          ▼          ▼
       GPT       Claude      Qwen
        │          │          │
    OpenAI API  Anthropic API  本地服务
        │          │          │
    API Key A   API Key B     通常无云端 Key
```

如果通过支持多模型的聚合服务，也可能使用一个平台的 API Key 调用多个模型。

但需要注意：**一个 API Key 能调用哪些模型，取决于服务商授权的模型范围，而不是 Agent 本身。**

---

# 四、你的 Multica + Codex 工作流能不能这样做？

可以，但要区分两个层次。

**第一层：Multica 调度不同模型或 Agent。**

例如：

```text
Multica
   │
   ├── GH Coding Agent
   │       └── Codex
   │
   ├── GH Research Agent
   │       └── Claude
   │
   └── GH Debug Agent
           └── DeepSeek
```

这是多个 Agent 使用不同模型。

**第二层：一个 GH Agent 内部调用多个模型。**

例如：

```text
GH Debug Agent
      │
      ▼
  Agent Runtime
      │
      ├── GPT
      ├── Qwen
      ├── Embedding
      └── Reranker
```

这才是严格意义上的一个 Agent 使用多个模型。

Multica 能否在同一个 Run 中原生切换模型，取决于它的具体版本和运行配置；即使没有原生支持，你开发的 GH Agent 也可以通过自己的代码实现模型路由。

# 五、如果是你的 DataTreeDoctor，我会怎么设计？

我建议分成三个开发阶段，而不是一开始就接入五六个模型。

| 阶段 | 技术组合 | 目标 |
|---|---|---|
| MVP | C# Analyzer | 准确识别和报告 Data Tree 问题 |
| V1 | C# + 一个 LLM | 用自然语言解释问题并提出建议 |
| V2 | C# + LLM + Embedding/RAG | 结合 GH 知识库进行诊断 |
| V3 | 多模型 Router + 本地/云端模型 | 根据复杂度、成本和隐私要求选择模型 |

最终可以发展成：

```text
                   DataTreeDoctor
                         │
                         ▼
                    C# Analyzer
                         │
                         ▼
                   Problem Router
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
       简单问题        中等问题        复杂问题
          │              │              │
       C# Rules       Local LLM      Cloud LLM
          │              │              │
          └──────────────┼──────────────┘
                         ▼
                   Diagnosis Result
                         │
                         ▼
                  Grasshopper UI
```

这里有一个关键的产品设计思想：

**不要为了使用多个模型而使用多个模型，而是让每个模型承担它真正擅长、且值得付费计算的任务。**

你未来的 GH Agent 可以根据任务难度决定是否调用 AI、调用本地模型还是云端模型，而不是让每一个数据树错误都消耗昂贵的推理 Token。

## 对话 5 · 10:32

### 用户

目前训练模型的方式有哪些？

### AI

目前训练 AI 模型的方式有很多，但它们并不是完全独立的技术，而是可以组合使用。

结合你最近学习的 **LLM、Agent、多模型架构、Embedding、具身智能和 Grasshopper 插件开发**，我建议你从三个层次理解：

1. **模型通过什么方式学习？**——训练方法
2. **模型处于哪个训练阶段？**——预训练、微调、对齐
3. **普通开发者如何让模型掌握专业知识？**——RAG、Fine-tuning、强化学习等

其中第三个层次与你未来开发 GH Agent 最相关。

# 一、首先理解：什么叫训练模型？

训练模型的本质是：

> 让模型通过大量数据和反馈，不断调整内部参数，使它在特定任务上的表现逐渐改善。

例如，你希望一个 AI 能够理解 Grasshopper 的 Data Tree。

最初，它可能无法准确判断：

```text
{0;0} → [A, B, C]
{0;1} → [D, E]
{1;0} → [F]
```

经过训练后，它可能逐渐学会：

- 理解数据树路径。
- 判断数据树结构。
- 分析不同组件之间的数据匹配关系。
- 识别异常的数据树操作。
- 给出合理的修改建议。

训练过程中，模型内部的参数（Weights）会发生变化。

这是理解训练与 RAG、Prompt Engineering 之间区别的关键。

---

# 二、按照学习方式分类：主要有六种

这是机器学习领域比较基础的一套分类方式。

| 训练方式 | 英文 | 简单理解 | 典型应用 |
|---|---|---|---|
| 监督学习 | Supervised Learning | 给模型问题和正确答案 | 分类、代码生成、指令微调 |
| 无监督学习 | Unsupervised Learning | 不直接提供人工标注答案，让模型发现数据规律 | 聚类、表示学习 |
| 自监督学习 | Self-Supervised Learning | 从原始数据自身构造训练目标 | LLM 预训练 |
| 半监督学习 | Semi-Supervised Learning | 少量标注数据 + 大量未标注数据 | 数据标注成本较高的任务 |
| 强化学习 | Reinforcement Learning | 通过奖励和惩罚学习策略 | 推理模型、机器人、Agent |
| 自蒸馏/知识蒸馏 | Knowledge Distillation | 用已有模型指导另一个模型 | 小模型训练、模型压缩 |

需要注意，知识蒸馏与前面几种不属于完全相同的分类维度，它可以结合监督学习或其他训练方法使用。

下面重点解释你需要掌握的几种。

## 1. 监督学习：给模型标准答案

这是最容易理解的训练方式。

例如，你收集了 10,000 个 GH Data Tree 问题，并给每个问题提供正确答案。

训练数据可能是：

```json
{
  "input": "Data Tree contains empty branches",
  "output": "Empty Branch Problem"
}
```

再例如：

```json
{
  "input": "Flatten changed the original tree structure",
  "output": "Tree Structure Loss"
}
```

模型不断学习：

```text
输入问题
   ↓
模型预测
   ↓
与标准答案比较
   ↓
计算误差
   ↓
调整模型参数
   ↓
继续训练
```

这种方式适合：

- 训练专门的分类模型。
- 让 LLM 学习特定的回答格式。
- 让模型适应专业领域的术语。
- 提高特定任务的执行能力。

**你以后如果想训练一个专门判断 GH 错误类型的小模型，就可以考虑监督学习。**

---

## 2. 自监督学习：让模型从数据本身学习

目前很多 LLM 的基础能力来自自监督预训练。

例如：

```text
输入：

Grasshopper is a visual programming
language for ______.

模型预测：

Rhino
```

训练系统并不一定需要人工为每句话编写问题和答案。

它可以从已有文本中自动构造学习目标。

现代自回归语言模型通常通过预测下一个 Token 进行预训练：

```text
大量文本
   ↓
切分 Token
   ↓
预测下一个 Token
   ↓
计算预测误差
   ↓
更新模型参数
```

经过大规模训练，模型逐渐学会语言结构、知识关联和一些推理模式。

但要注意：

**预测下一个 Token 是训练目标，不代表模型只能机械地补全文字。**

模型最终表现出来的能力，还取决于架构、数据、训练规模和后续训练等因素。

---

## 3. 强化学习：通过反馈优化行为

强化学习与你研究的 Agent 特别相关。

假设你开发了一个能够自动修改 GH Definition 的 Agent。

它需要完成：

```text
用户：
修复这个 Data Tree 错误。
```

Agent 执行：

```text
分析 Definition
      ↓
选择操作
      ↓
修改组件
      ↓
运行 Grasshopper
      ↓
检查结果
```

你可以设计奖励机制：

| 行为结果 | 奖励示例 |
|---|---:|
| 成功修复数据树 | +10 |
| 保持原有几何结果正确 | +5 |
| 引入新的组件错误 | -10 |
| 修改后 Definition 无法运行 | -20 |

这些数字只是演示，不是实际推荐的奖励函数。

模型通过大量尝试与反馈，逐渐优化决策策略。

但这里需要区分：

**Agent 在运行时不断尝试、检查和修正，并不自动等于强化学习。**

只有当这些反馈被用于更新模型参数或训练策略时，才涉及真正的模型训练。

普通 Agent Loop：

```text
尝试
 ↓
检查
 ↓
重新尝试
 ↓
完成任务
```

强化学习训练：

```text
尝试
 ↓
获得奖励
 ↓
更新模型参数
 ↓
下一轮训练
```

两者非常容易被初学者混淆。

# 三、按照模型开发阶段分类

这一套分类对理解 GPT、Claude、DeepSeek 等模型的开发过程更重要。

一个大语言模型通常不是训练一次就结束。

可以把它理解成：

```text
原始模型
   │
   ▼
Pre-training
预训练
   │
   ▼
Base Model
基础模型
   │
   ▼
Post-training
后训练
   │
   ├── SFT
   │   监督微调
   │
   ├── Preference Optimization
   │   偏好优化
   │
   └── Reinforcement Learning
   │   强化学习
   │
   ▼
Instruction / Chat Model
指令或对话模型
```

这是一种概念性流程，具体模型的训练顺序和技术组合会有所不同。

## 1. Pre-training：预训练

目标是建立广泛的基础能力。

数据可能包括：

- 文本
- 代码
- 图像
- 视频
- 音频
- 其他结构化数据

例如：

```text
互联网文本
+
书籍
+
代码
+
专业文档
       ↓
大规模训练
       ↓
Base Model
```

这一步通常需要大量计算资源。

对于你现在的 GH Agent 项目，**不建议从零预训练一个 LLM**，因为成本和数据需求都非常高。

---

## 2. SFT：监督微调

SFT 全称：

**Supervised Fine-Tuning**

它是在已有模型的基础上，继续使用高质量的输入和目标输出进行训练。

例如：

基础模型已经知道什么是 Grasshopper。

但你希望它按照专业 GH 调试工程师的方式回答：

```text
用户：
为什么 Flatten 后几何数量不对？

目标回答：

1. 检查 Flatten 前的数据树结构。
2. 对比 Flatten 后的 Branch 数量。
3. 检查下游组件的数据匹配方式。
4. 判断是否发生非预期的数据组合。
5. 给出可验证的修改建议。
```

你收集大量这样的数据：

```text
GH 问题 → 专业诊断
GH 问题 → 专业诊断
GH 问题 → 专业诊断
```

然后微调现有模型。

这样就不需要从零训练。

---

## 3. 偏好优化：让模型学习什么回答更符合目标

例如，对于同一个问题：

**回答 A：**

> 你的数据树错了，Flatten 一下就行。

**回答 B：**

> 首先检查输入端的 Branch 数量和 Path，再确认下游组件的数据匹配关系。Flatten 可能改变数据结构，因此不建议在未验证原因前直接使用。

你可以构建偏好数据：

```text
Prompt
   ↓
回答 A
回答 B
   ↓
标注：
B 更符合专业诊断要求
```

再使用 DPO 等方法进行偏好优化。

这里的 DPO 是：

**Direct Preference Optimization**

它与基于人类反馈的强化学习（RLHF）有关联，但 DPO 本身不需要采用传统 RLHF 中显式训练奖励模型、再进行在线强化学习的完整流程。

---

# 四、真正与你有关的：普通开发者如何训练自己的专业模型？

现在假设你要做：

> 一个真正懂 Grasshopper、参数化设计、Data Tree、RhinoCommon 和建筑几何的专业 AI Agent。

你有五条值得了解的技术路线。

| 方式 | 是否改变模型参数 | 主要用途 | 开发成本 |
|---|---|---|---|
| Prompt Engineering | 否 | 规定模型角色和行为 | 低 |
| RAG | 否 | 让模型使用外部知识库 | 低至中 |
| SFT | 是 | 让模型适应专业任务和输出方式 | 中至高 |
| LoRA / QLoRA | 是，通常只训练少量附加参数 | 降低微调资源需求 | 中 |
| 强化学习 | 是 | 优化多步骤决策和行为 | 高 |

这里有一个非常重要的区别：

**Prompt 和 RAG 不是严格意义上的模型训练。**

它们可以显著改善模型在某个领域的表现，但不会直接修改基础模型的权重。

## 1. Prompt Engineering

你可以直接告诉模型：

```text
你是一个 Grasshopper Data Tree Debug Agent。

你的职责：

1. 分析数据树结构。
2. 识别潜在错误。
3. 不要随意建议 Flatten。
4. 优先通过 GH SDK 获取真实数据。
5. 输出可验证的修改建议。
```

这是最简单的专业化方式。

---

## 2. RAG：给模型建立外部知识库

这是我认为你目前最值得学习的技术之一。

例如，你已经在使用 Obsidian 建立 Agent 学习知识库。

未来也可以为 GH Agent 建立专业知识库：

```text
Grasshopper 官方文档
+
RhinoCommon API
+
GH Data Tree 案例
+
常见错误解决方案
+
你的个人经验
          ↓
     Embedding
          ↓
     Vector Database
          ↓
        RAG
          ↓
       GH Agent
```

当用户问：

> 为什么我的数据树路径变成了 `{0;0;0}`？

系统可以先搜索相关资料，再交给 LLM 分析。

RAG 的优势是：

**知识可以不断更新，而不需要每增加一篇文档就重新训练模型。**

---

## 3. LoRA：低成本微调

LoRA 全称：

**Low-Rank Adaptation**

它不需要像完整微调那样更新全部模型参数，而是通过训练少量附加参数来适配模型。

可以简单理解为：

```text
基础模型
   │
   ├── 原有参数
   │
   └── LoRA Adapter
          │
          ▼
      GH 专业能力适配
```

例如：

```text
Qwen 基础模型
      +
GH Data Tree 微调数据
      ↓
LoRA Training
      ↓
GH 专业模型
```

你可以在自己的电脑或租用 GPU 服务器完成部分开源模型的 LoRA 微调。

但实际硬件需求取决于模型大小、量化方式、序列长度和训练配置。

# 六、最后再补充：多模态和机器人模型的训练有所不同

因为你也在研究具身智能，所以需要知道，LLM 并不是所有 AI 训练的唯一范式。

| 研究方向 | 常见训练目标或方法 |
|---|---|
| LLM | Token 预测、SFT、偏好优化、强化学习 |
| 图像生成 | 扩散训练、流匹配等 |
| 视频模型 | 视频预测、时空表示学习、生成式训练 |
| 世界模型 | 预测未来状态、学习环境表征 |
| 机器人动作模型 | 模仿学习、行为克隆、强化学习 |
| Embedding 模型 | 对比学习、相似度学习 |
| Reranker | 相关性监督、排序损失、偏好学习 |

例如，机器人可以通过人类示范学习动作：

```text
人类操作机械臂
       ↓
记录视觉和动作数据
       ↓
模型学习
       ↓
机器人模仿动作
```

这叫 **Imitation Learning（模仿学习）**。

其中一种常见方法是 Behavior Cloning（行为克隆）。

它与你之前了解的 Agent Loop 有联系，但涉及的训练数据和目标不同。

## 对话 6 · 10:41

### 用户

LM,LLM,RLHF,RLVR,RLCD分别都是什么

### AI

这五个词正好能串起你刚才问的两个问题：**大模型是什么，以及大模型是怎么训练出来的。**

尤其是 RLHF、RLVR、RLCD，它们的区别不是模型大小，而是**训练模型时，用什么标准判断模型做得好不好**。

先看一张总表：

| 缩写 | 英文全称 | 中文理解 | 核心作用 |
|---|---|---|---|
| LM | Language Model | 语言模型 | 理解、预测或生成语言 |
| LLM | Large Language Model | 大语言模型 | 具备大规模参数和广泛语言能力的模型 |
| RLHF | Reinforcement Learning from Human Feedback | 基于人类反馈的强化学习 | 让模型学习人类偏好的回答 |
| RLVR | Reinforcement Learning with Verifiable Rewards | 基于可验证奖励的强化学习 | 让模型学习产生能够被客观验证的结果 |
| RLCD | Reinforcement Learning for Calibrated Decisions | 面向校准决策的强化学习 | 让模型给出的概率与实际正确率相匹配 |

**这里的 RLCD 按照你上一轮提到的 Jev 模型来解释。** 需要特别说明：2024 年已有一篇论文也使用 RLCD 这个缩写，但它指的是 *Reinforcement Learning from Contrastive Distillation（基于对比蒸馏的强化学习）*，与 Jev 所说的 RLCD 不是同一方法。:chatgpt-content-reference{index="0"}

# 一、LM：Language Model（语言模型）

LM 是最基础的概念。

简单理解：

> **语言模型是学习语言规律，并能够对语言进行预测或生成的模型。**

例如：

输入：

```text
Grasshopper is a visual programming...
```

模型可能预测下一个词是：

```text
language
```

但 LM 不一定非常大，也不一定具有聊天能力。

你可以把它理解为一个大类别：

```text
Language Model
语言模型
    │
    ├── 小型语言模型
    │
    └── 大语言模型
```

---

# 二、LLM：Large Language Model（大语言模型）

LLM 就是大语言模型。

GPT、Claude、DeepSeek、Qwen 等模型家族中都有 LLM。

与一般语言模型相比，LLM 通常具有更大的参数规模、更丰富的训练数据和更广泛的任务能力。

例如：

```text
用户：
帮我检查这个 Grasshopper Definition
为什么数据树发生了错误？
```

LLM 可以：

1. 理解问题。
2. 分析输入数据。
3. 推理可能原因。
4. 生成修改建议。
5. 调用工具进一步验证。

不过，调用工具并不是 LLM 自身必然具备的能力，而是模型与 Agent Runtime、API、Tools 等系统结合后的结果。

**LM 和 LLM 的关系：LLM 是 LM 的一个子类。**

---

# 三、RLHF：让模型学习人类喜欢什么回答

RLHF 全称：

**Reinforcement Learning from Human Feedback**

中文叫基于人类反馈的强化学习。

假设我们正在训练一个 GH 专业模型。

用户提问：

> 为什么我的 Grasshopper 数据树出错了？

模型生成两个回答。

**回答 A：**

> 数据树有问题，Flatten 一下就行。

**回答 B：**

> 首先检查数据树路径、Branch 数量和下游组件的数据匹配方式。Flatten 可能破坏原有结构，需要先确认问题原因。

人类标注人员判断：

```text
回答 A：较差

回答 B：较好
```

训练系统利用这些偏好数据，让模型逐渐倾向于生成更符合人类要求的回答。

经典 RLHF 流程可以简化为：

```text
基础 LLM
    ↓
生成多个回答
    ↓
人类比较回答
    ↓
训练奖励模型
    ↓
奖励模型提供评分
    ↓
强化学习更新 LLM
```

**RLHF 的核心问题是：人类更喜欢哪种回答？**

但它也有局限：人类觉得某个回答清晰、流畅、有说服力，不代表它在技术上一定正确。

---

# 四、RLVR：让模型学习产生可以验证的正确结果

RLVR 全称：

**Reinforcement Learning with Verifiable Rewards**

它与 RLHF 的关键区别在于：

**不一定需要人类判断回答好不好，而是通过客观的验证机制判断结果。**

例如数学问题：

```text
问题：

25 × 16 = ?
```

模型输出：

```text
400
```

程序验证：

```text
400 == 25 × 16

True
```

模型获得奖励。

如果模型输出：

```text
450
```

程序验证：

```text
450 == 25 × 16

False
```

模型无法获得正确答案对应的奖励。

这种方法也适用于代码训练。

例如你的 DataTreeDoctor：

```text
GH Agent
   ↓
生成修复代码
   ↓
执行代码
   ↓
运行单元测试
   ↓
检查是否成功
   ↓
生成奖励信号
```

假设模型修改了一段 C# 代码：

```csharp
if (branch.Count == 0)
{
    ReportEmptyBranch();
}
```

然后运行测试。

```text
测试通过 → 正向奖励

测试失败 → 无奖励或负向奖励
```

训练系统可以利用大量这样的反馈更新模型。

**RLVR 的核心问题是：结果是否通过了可验证的检查？**

不过，测试通过不一定代表代码完全正确，RLVR 的效果仍取决于验证器和测试覆盖范围。

---

# 五、RLCD：让模型知道自己有多大把握

这是你刚才提到的 Jev 模型所使用的术语。

RLCD 全称：

**Reinforcement Learning for Calibrated Decisions**

中文可以理解为：

**面向校准决策的强化学习。**

TypeSafe AI 将其描述为 Jev 的训练方法，目标是让模型给出的概率与实际结果相匹配。不过，截至 2026 年 9 月，公开资料尚不足以独立复现其具体训练算法。:chatgpt-content-reference{index="1"}

### 什么叫校准（Calibration）？

假设一个模型进行了 100 次判断。

每次都说：

> 我有 90% 的把握。

如果它实际正确了 90 次：

```text
预测置信度：90%

实际正确率：90%
```

说明它在这组预测上的置信度是校准的。

如果只正确了 60 次：

```text
预测置信度：90%

实际正确率：60%
```

说明它过度自信。

如果正确了 99 次：

```text
预测置信度：90%

实际正确率：99%
```

说明它可能过于保守。

注意，校准是针对大量预测的统计性质，并不是说单次预测标注 90% 就能保证正确。

### 放到你的 GH Agent 中

假设你的 GH Agent 检测到一个复杂问题。

Jev 这样的决策模型可能输出：

```json
{
  "problem": "Data Matching Error",
  "confidence": 0.96
}
```

你的程序可以根据经过验证的置信度设计处理策略：

```text
GH Analyzer
      ↓
决策模型
      ↓
输出问题类型 + 置信度
      │
      ├── 高置信度
      │      ↓
      │   给出诊断建议
      │
      ├── 中等置信度
      │      ↓
      │   调用强推理模型
      │
      └── 低置信度
             ↓
         请求用户确认
```

这里的置信度阈值需要通过实际数据验证，不能直接把模型输出的数字当作可靠保证。

# 六、RLHF、RLVR、RLCD 最核心的区别

假设你问三个经过不同训练目标优化的模型：

> 这个 Grasshopper Definition 的问题是什么？

它们可能分别受到不同奖励标准的影响：

| 训练方式 | 奖励关注点 | 通俗理解 |
|---|---|---|
| RLHF | 人类偏好的回答 | 人觉得回答好不好？ |
| RLVR | 可验证的结果 | 程序能否证明结果正确？ |
| RLCD（Jev） | 概率与实际正确率的匹配 | 模型知道自己有多大把握吗？ |

注意，这不是说一个模型只能采用其中一种方法。实际模型训练可以组合多种训练目标。

### AI

你框出来的三个部分，分别是 **Pre-training（预训练）、SFT（监督微调）和 Post-training（后训练）**。

它们描述的是一个大语言模型从基础能力到能够按照人类要求完成任务的训练过程。

不过，先纠正一下我上一张图中的一个不够严谨的地方：

**SFT 本身通常就属于 Post-training（后训练），不是与后训练完全并列的独立阶段。**

正确的关系应该是：

```text
           Pre-training
              预训练
                │
                ▼
            Base Model
             基础模型
                │
                ▼
           Post-training
              后训练
                │
       ┌────────┼────────┐
       ▼        ▼        ▼
      SFT      RLHF     RLVR
    监督微调  人类反馈  可验证奖励
                │
                ▼
           最终可用模型
```

下面分别解释。

## 1. Pre-training：预训练

**目的：让模型获得广泛的基础能力。**

假设我们要从零开发一个 AI 模型。

首先需要准备大量数据：

```text
互联网文本
    +
书籍
    +
代码
    +
专业资料
    +
其他训练数据
    ↓
Pre-training
    ↓
Base Model
```

模型在这个阶段学习语言、知识、代码规律和各种概念之间的关系。

例如，它可能学会：

- Grasshopper 是什么。
- Python 的语法。
- 建筑设计的基本概念。
- 数学和逻辑规律。
- 如何预测下一个 Token。

但是，经过预训练的基础模型不一定擅长按照用户指令进行对话。

例如，你输入：

> 请解释 Grasshopper Data Tree。

基础模型可能继续生成类似百科文章的内容，而不一定按照你期望的方式解释。

因为它主要接受的是大规模基础训练，而不是专门学习如何当一个助手。

---

## 2. SFT：监督微调

全称：**Supervised Fine-Tuning**

**目的：教模型如何按照要求完成具体任务。**

这时候我们已经有了一个预训练完成的基础模型，不需要从零开始。

我们给它大量高质量的「问题—理想回答」示例。

例如：

| 用户问题 | 理想回答 |
|---|---|
| 什么是 GH Data Tree？ | 用初学者能够理解的方式解释数据树 |
| 什么是 Flatten？ | 解释 Flatten 的作用及其潜在问题 |
| 如何检查 Empty Branch？ | 给出具体检查步骤 |
| 如何使用 RhinoCommon？ | 提供正确的 C# 代码示例 |

训练流程：

```text
Base Model
    │
    ▼
高质量问答数据
    │
    ▼
SFT
    │
    ▼
Instruction Model
指令模型
```

经过 SFT 后，模型通常更善于理解和执行指令，并遵循特定的输出格式。

### 用你的 GH Agent 举例

你希望模型回答 GH 问题时始终采用：

```text
1. 问题定位
2. 原因分析
3. 修改建议
4. 验证方法
```

就可以通过大量这种格式的专业示例进行 SFT。

不过，如果只是希望模型遵循这个格式，最初完全可以用 Prompt 实现，不必马上微调。

---

## 3. Post-training：后训练

**目的：在基础模型已经具备广泛能力后，进一步改善它完成实际任务的表现。**

后训练不是单一的训练算法，而是一组训练方法的统称。

SFT、RLHF、RLVR 都可以属于后训练。

例如：

```text
                 Base Model
                     │
                     ▼
               Post-training
                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼
       SFT          RLHF         RLVR
        │            │            │
    学习示范      学习人类偏好   学习可验证结果
        │            │            │
        └────────────┼────────────┘
                     ▼
                最终模型
```

这三种方法分别解决不同的问题。

| 方法 | 主要解决的问题 | 举例 |
|---|---|---|
| SFT | 模型应该怎样回答？ | 学习专业 GH 诊断格式 |
| RLHF | 什么样的回答更符合人类偏好？ | 避免敷衍、无依据的建议 |
| RLVR | 怎样得到能够验证的正确结果？ | 生成代码并通过测试 |

它们可以组合使用，但不是所有模型都必须采用全部方法。

---

## 最后，用一个你熟悉的例子记住它们

假设我们要培养一位 Grasshopper 专业工程师。

| 模型训练阶段 | 培养工程师的过程 |
|---|---|
| Pre-training | 学习数学、建筑、编程、Grasshopper 等基础知识 |
| SFT | 跟着老师学习如何分析问题、写代码和回答用户 |
| RLHF | 根据用户和专家的反馈改善回答方式 |
| RLVR | 通过运行代码、检查几何结果和测试来验证解决方案 |

**一句话总结：**

Pre-training 让模型建立基础能力；Post-training 让模型更好地完成实际任务；SFT 是 Post-training 中一种重要的方法，主要通过高质量示范来训练模型。
